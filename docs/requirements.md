# Feature Summary
ระบบ IT Ticket Tracker (MVP) ใช้สำหรับรับแจ้งปัญหาไอทีภายในองค์กรและติดตามสถานะงานแบบง่าย โดยรองรับการสร้าง ticket, ดูรายการ ticket, กรองรายการตามสถานะ, อัปเดตสถานะ และแสดงสรุปจำนวน ticket ตามสถานะเพื่อให้ทีมงานมองภาพรวมได้รวดเร็ว

# User Stories
- ในฐานะพนักงาน ฉันต้องการสร้าง ticket แจ้งปัญหา เพื่อให้ทีมไอทีรับทราบและเริ่มดำเนินการ
- ในฐานะพนักงาน ฉันต้องการดูรายการ ticket ทั้งหมด เพื่อให้ตรวจสอบสถานะงานของฉันได้
- ในฐานะผู้ใช้งาน ฉันต้องการกรองรายการตามสถานะ เพื่อให้หางานที่ต้องติดตามได้ง่าย
- ในฐานะเจ้าหน้าที่ไอที ฉันต้องการอัปเดตสถานะ ticket เพื่อให้สะท้อนความคืบหน้าล่าสุด
- ในฐานะหัวหน้างาน ฉันต้องการดู summary counts เพื่อให้ประเมินปริมาณงานในแต่ละสถานะได้เร็ว

# Acceptance Criteria
- ระบบต้องสร้าง ticket ใหม่ได้และกำหนด `id` ที่มีรูปแบบขึ้นต้นด้วย `TKT-xxx` โดย `xxx` คือเลข 3 หลัก
- ระบบต้อง validate ฟิลด์ที่กำหนดเป็น required ก่อนบันทึกข้อมูล
- ระบบต้องรองรับ `category` เฉพาะค่า `Hardware`, `Software`, `Network`, และ `Account`
- ระบบต้องรองรับ `priority` เฉพาะค่า `Low`, `Medium`, และ `High`
- ระบบต้องรองรับ `status` เฉพาะค่า `Open`, `In Progress`, และ `Resolved`
- ระบบต้องกำหนดค่าเริ่มต้นของ `status` เป็น `Open` เมื่อสร้าง ticket ใหม่
- ระบบต้องแสดงรายการ ticket ทั้งหมดได้
- ระบบต้องกรองรายการ ticket ตาม `status` ที่เลือกได้
- ระบบต้องอัปเดตสถานะของ ticket ได้ตามค่าที่ระบบอนุญาต
- ระบบต้องแสดง summary counts ของ ticket ตามสถานะอย่างถูกต้องและสอดคล้องกับข้อมูลในรายการ

# Edge Cases
- หากผู้ใช้ไม่กรอกฟิลด์ required ระบบต้องไม่บันทึก ticket และต้องแจ้ง validation error
- หาก `category` ถูกส่งมาเป็นค่าที่ไม่อยู่ในชุดที่กำหนด เช่น `Printer` หรือ `Email` ระบบต้องปฏิเสธข้อมูล
- หาก `priority` ถูกส่งมาเป็นค่าที่ไม่อยู่ในชุดที่กำหนด ระบบต้องปฏิเสธข้อมูล
- หาก `status` ถูกสร้างหรืออัปเดตเป็นค่าที่ไม่อยู่ในชุดที่กำหนด ระบบต้องไม่ยอมรับการเปลี่ยนแปลง
- หาก `id` ไม่ตรงรูปแบบ `TKT-xxx` เช่น ขาด prefix, มีตัวอักษรเกิน, หรือเลขไม่ครบ 3 หลัก ระบบต้องไม่ยอมรับค่า
- หากไม่มี ticket ในสถานะที่เลือกสำหรับการ filter ระบบต้องแสดงผลเป็น empty state แทนการแสดงข้อมูลผิดพลาด
- หากมีการอัปเดตสถานะเป็นค่าซ้ำเดิม ระบบควรไม่ทำให้ข้อมูลเพี้ยนหรือสร้างผลกระทบกับ summary counts
- หาก summary counts ไม่ตรงกับจำนวนรายการที่แสดง ต้องถือเป็นความไม่สอดคล้องของข้อมูลและต้องตรวจสอบ logic การนับ
- หากข้อมูล ticket ถูกลบหรือแก้ไขระหว่างที่ผู้ใช้กำลังดูรายการ ระบบควรรีเฟรชข้อมูลให้สอดคล้องกับสถานะล่าสุด
